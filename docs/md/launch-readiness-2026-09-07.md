# Glassy Desk launch readiness — 7 September 2026

> This is the original audit of `485335b`. See the [subsequent hardening and release validation](launch-hardening-2026-09-07.md) for implemented fixes and the explicitly deferred iCloud scope.

**Verdict: hold the broad Fast Connection launch.** The native streaming foundation and Mac distribution pipeline are viable, but current source still has reproducible congestion/recovery defects, a production identity fallback defect, and incomplete privacy/release validation. This is a focused hardening effort; the evidence does not justify replacing the whole architecture.

Reviewed commit: `485335b` (initial working tree clean). Target: iOS/iPadOS **1.3 (3)** with the separately distributed Mac companion **0.2.9 (13)**. The public US App Store already lists iOS **1.2** and mentions Glassy Stream. This assessment concerns the upcoming release and broader promotion, rather than creation of the first App Store listing. No app implementation or remote configuration was changed during the audit.

## Fix before broad launch

### 1. P1 — Fast Connection falls seconds behind on constrained links

The current production transport, compiled with optimization and carrying authenticated encrypted synthetic media through a 2 Mbps proxy, delivered **3,770 ms p95 frame callback age**, **3,935 ms maximum**, and **3,418 ms ping-response callback delay**. Offered payload was 9.38 Mbps and quality stayed `best`. Manually reducing the source to 0.73 Mbps on the same cap reduced p95 age to **43.6 ms**.

These are transport-callback measurements, not physical capture-to-display latency or keyboard latency. Frames not observed before the experiment ended may remain buffered; they are not a measured drop count.

The host uses fixed 2/5/12 Mbps presets ([HostStreamQualityConfiguration.swift](../../GlassyHost/Sources/GlassyHost/Models/HostStreamQualityConfiguration.swift#L7)), starts the client at Best ([SessionPreferences.swift](../../dejaview/Models/SessionPreferences.swift#L11)), permits 10 queued messages or 24 MiB without an age budget, and shares a FIFO between media and downstream control/telemetry ([HostServer.swift](../../GlassyHost/Sources/GlassyHost/Services/HostServer.swift#L1253)). The client ignores pong feedback ([GlassyStreamSessionController.swift](../../dejaview/Services/GlassyStream/GlassyStreamSessionController.swift#L271)).

**Minimum remedy:** receiver-progress/queue-age instrumentation, bounded media admission, and automatic bitrate/FPS/resolution adaptation. Manual Data Saver is a useful fallback but does not establish the advertised experience across mobile/VPN links. Changing quality currently restarts capture and recreates the encoder ([HostController.swift](../../GlassyHost/Sources/GlassyHost/Stores/HostController.swift#L1113)); frequent adaptation needs a less disruptive bitrate path. Packets are sequenced/encrypted before queuing, so reordering already encrypted control packets is unsafe. Allocate sequence numbers in final send order or define separate channel domains.

### 2. P1 — A busy iOS main thread retains stale media before the renderer

Each callback captures a payload in a new asynchronous dispatch block ([GlassyStreamClient.swift](../../dejaview/Services/GlassyStream/GlassyStreamClient.swift#L795)), and the session targets the main queue ([GlassyStreamSessionController.swift](../../dejaview/Services/GlassyStream/GlassyStreamSessionController.swift#L179)). The renderer's latest pending slot sits downstream of that unbounded queue.

The one-second stalled-consumer probe delivered all 180 frames afterward, including **41 over 100 ms old** and **22 over 500 ms old**; p95 was **837 ms**, maximum **1,009 ms**.

**Minimum remedy:** a bounded serial media worker and one scheduled drain, with byte/count/age limits. Preserve configuration and H.264 reference-frame ordering; after dropping required reference data, request a fresh keyframe. Move sample preparation off main while keeping view/layout state there. An indiscriminate newest-element buffer can corrupt decoding.

### 3. P1 — Recovery can wait for someone to change the Mac's screen

[H264Encoder.requestKeyFrame](../../GlassyHost/Sources/GlassyHost/Services/H264Encoder.swift#L129) only flags the next submitted frame. Capture accepts complete changed frames ([ScreenCaptureService.swift](../../GlassyHost/Sources/GlassyHost/Services/ScreenCaptureService.swift#L406)). A joining viewer gets cached configuration followed by a keyframe request ([HostServer.swift](../../GlassyHost/Sources/GlassyHost/Services/HostServer.swift#L1116)).

The real VideoToolbox diagnostic produced **zero outputs for one second after a keyframe request without new capture input**; the next supplied input produced a keyframe. A second viewer, display reattachment, or decoder recovery can therefore wait for desktop activity. A real static-desktop reproduction is still needed to measure the UI delay; the encoder behavior is confirmed.

**Minimum remedy:** retain one valid latest capture buffer and re-encode it on a coalesced recovery request. Clear it on display/capture-generation changes and avoid continuous idle encoding.

### 4. P1 — A Keychain failure can silently change the Mac's trusted identity

Production packaging explicitly selects Keychain storage, confirmed in the final signed app. Nevertheless, [PairingSecretStore.swift](../../GlassyHost/Sources/GlassyHost/Services/PairingSecretStore.swift#L55) catches unavailable/authentication-denied Keychain statuses and loads or creates a separate file-based root. The next launch can switch back when the original Keychain becomes accessible. Existing users then see a different-Mac identity error, while pairings created under the fallback root stop working later. `replace()` has the same fallback at line 73, so a reported root replacement may leave the original Keychain root unchanged. Invalid root length also causes silent replacement.

**Minimum remedy:** explicit file mode for development only; production fails closed with an actionable retry/recovery path. Treat corrupt root data as an error. Inject Keychain failure cases and verify that neither launch nor reset changes identity implicitly. Exercise a signed existing-user upgrade and locked/unlocked login Keychain before release. This is a code-confirmed failure path, not a report that the current machine's credentials are damaged.

### 5. P1 — First-party privacy declarations are missing

There is no app-authored `PrivacyInfo.xcprivacy` in the repository. Inspection of the built iOS app found only RevenueCat and CryptoSwift resource manifests, and no app/widget manifest. First-party code directly uses UserDefaults and `ProcessInfo.systemUptime` ([VNCSession.swift](../../dejaview/Services/RemoteSession/VNCSession.swift#L667)). SDK manifests do not document all of this app's own API use.

**Minimum remedy:** inventory required-reason APIs in the app and extension, add accurate declarations to their resources, and inspect the exact release archive/privacy report. Apple requires the relevant declarations and documents the app-bundle placement. This is a packaging gap; an App Store Connect upload rejection was not observed here. [Apple privacy manifest guidance](https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk), [required-reason APIs](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api).

### 6. P1 — Published privacy information lags behind the shipped analytics model

The [published policy](https://bunn.dev/glassydesk/privacy.html), dated July 24, describes RevenueCat purchase processing but omits Cloudflare aggregate analytics and nonpurchase milestones attached to RevenueCat customers. It scopes itself to iPhone/iPad and predates the Mac companion/camera pairing behavior. The [live US listing](https://apps.apple.com/us/app/glassy-desk/id6787767486) shows only Purchases under Data Linked to You.

Current source defaults analytics on ([AnalyticsTracking.swift](../../dejaview/Services/Analytics/AnalyticsTracking.swift#L6)), posts aggregate events to `analytics.bunn.dev` ([CloudflareAnalytics.swift](../../dejaview/Services/Analytics/CloudflareAnalytics.swift#L23)), and writes session-funnel attributes to RevenueCat customer records ([FunnelMilestoneTracking.swift](../../dejaview/Services/Analytics/FunnelMilestoneTracking.swift#L197)). The Settings statement that no identifiable information is ever sent overstates the distinction between anonymous aggregates and pseudonymous customer-linked events. There is no dedicated Privacy Policy link in Settings/About; a remote paywall footer is not a reliable universal access path, especially for existing Pro users.

**Minimum remedy:** reconcile policy, consent behavior, Settings copy, app manifests, and App Store privacy answers against actual collection. Describe Cloudflare and RevenueCat purposes separately, and make policy/terms directly accessible. Verify opt-out stops optional collection, including queued work. This is not evidence of advertising tracking or a reason to add ATT indiscriminately. Apple requires an accessible policy and disclosure of integrated partners' collection. [App Review Guidelines 5.1.1](https://developer.apple.com/app-store/review/guidelines/#privacy), [App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/).

**Credential storage is a durable product decision.** VNC account passwords are intentionally copied into SwiftData and a CloudKit encrypted field, as well as Keychain ([SavedMachineRecord.swift:18](../../dejaview/Models/Persistence/SavedMachineRecord.swift#L18), [repository](../../dejaview/Services/Machines/SwiftDataSavedMachineRepository.swift#L184)). `allowsCloudEncryption` is present, and the public policy already discloses cloud password storage; this review does not claim CloudKit stores them in plaintext. Validate local-store data protection and decide whether broad sync of Mac account passwords remains the intended promise. Fast Connection credentials are device-local, so a machine syncing to another iPhone/iPad does not also transfer approval. Make that setup expectation explicit.

**Treat the existing CloudKit schema and identities as compatibility commitments.** No explicit VersionedSchema is present, but the current optional/additive fields are not by themselves proof of a broken migration. Preserve a real 1.2 database fixture and test 1.3 upgrades. Verify production schema deployment; development/simulator success cannot establish it. Apple does not allow deleting already deployed record types/fields, so use additive migrations and retain old identifiers rather than renaming `iCloud.dev.bunn.dejaview` for branding. [Apple schema deployment guidance](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema).

**Do not require simultaneous Mac/iOS updates.** Both peers accept wire version 1 only; unknown message kinds/flags are fatal ([HostProtocol.swift:291](../../GlassyHost/Sources/GlassyHost/Services/HostProtocol.swift#L291), [GlassyStreamWire.swift:128](../../dejaview/Services/GlassyStream/GlassyStreamWire.swift#L128)). Existing optional quality, cursor, password, and clipboard support is sensibly capability-gated. Continue v1 support and negotiated opt-in for extensions; an incompatible change needs overlapping dual-protocol support. The 0.2.7 and 0.2.9 protocol/auth files are unchanged, so the stale download link is not evidence of a protocol mismatch; it omits the 0.2.9 shifted-keyboard fix.

**Keep the distribution model explicit.** The native host is a direct-download Developer ID app using Sparkle and empty sandbox entitlements. This is appropriate for the inspected release path. It is not a Mac App Store-ready package: Apple requires sandboxing and Store-provided updates for that channel. A native Mac App Store product would need a separate feasibility pass, especially for input control. The public iOS listing's ability to run on Apple silicon Macs is not the native host. [Mac App Store rules 2.4.5](https://developer.apple.com/app-store/review/guidelines/#hardware-compatibility).

## Launch gates still requiring evidence

1. **Paid access and actual Release paywall.** [SubscriptionStore.refresh](../../dejaview/Services/Subscriptions/SubscriptionStore.swift#L47) awaits offerings before customer info; [app startup](../../dejaview/App/DejaViewApp.swift#L58) begins the info stream afterward. Until info arrives the app treats access as free. RevenueCat's own startup/offline handling can mitigate this, so an offline paid-user disconnect is not yet reproduced. Decouple entitlement bootstrap from offering fetches and test a paid installation with LAN access but no internet, delayed/failed offerings, restart, restore, cancellation/refund, all three products, and expired subscriptions. Debug uses a Test Store key; Release uses an App Store key. Standalone Restore/Customer Center is not generally reachable in Release, making the actual remotely configured paywall's restore/terms/privacy controls a release gate. Keep the existing `Glassy View Pro` entitlement and product identifiers compatible.
2. **Private Store state.** Run `asc validate --app 6787767486 --version 1.3 --platform IOS --deep --output table` once authenticated, plus relevant IAP/subscription validators. Verify attached processed build, review instructions/demo access, screenshots, products, agreements, price/availability, age rating and privacy publication. Local `.asc/metadata/version` only contains 1.1; that is stale local evidence, not proof that live 1.3 metadata is missing. Explain the companion setup and every significant new feature to Review. Apple requires complete, accessible functionality; general desktop mirroring is distinct from the special restrictions for mirroring specific software/services. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/).
3. **Exact signed iOS archive.** This audit's device build disables signing. Verify App Store provisioning, final entitlements, production CloudKit schema, privacy report and upload validation on the actual archive. Reassess the hard-coded `ITSAppUsesNonExemptEncryption=false` using the full CryptoKit/custom protocol and RoyalVNC/CryptoSwift inventory; the value is not proof of exemption. Do not change it based only on an assumption. [Apple export-compliance process](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance/).
4. **Physical runtime matrix.** Test real iPhone and iPad, macOS 14 and current macOS, Apple silicon and supported Intel hardware. Cover first install, all permission denial/regrant paths, locked screen, sleep/wake, restart/login, unplug/replug display, external-display attachment, keyboard layouts/IME, clipboard, app background/foreground, Wi-Fi/mobile/Tailscale route transitions, revoked pairing, one slow plus one fast viewer, and upgrading the installed companion while sessions exist. Distinguish restart-before-login/FileVault limitations from ordinary sleep. Include VoiceOver, Dynamic Type, reduced motion and touch targets in the client controls/setup flows before declaring accessibility support.
5. **Performance acceptance.** Use real H.264 workloads at 0.5/1/2/5 Mbps with 50–150 ms RTT, jitter, 1%/3% loss and a one-second UI stall. Require automatic adaptation, bounded retained media, fresh recovery without host activity, and no reconnection/keyframe storms. Record actual presentation and input-to-visible-response, memory, CPU, energy and thermal state in a sustained Release run. `renderedFrameCount` currently increments at enqueue, so it is not displayed-frame evidence. The prior review's 100–150 ms software queue budget is an initial tuning target, not a universal total-latency guarantee.
6. **Release surfaces and dependency continuity.** Update the [Mac setup page](https://bunn.dev/glassydesk/mac/) from its verified 0.2.7 link to the release actually qualified. Verify public DMG/ZIP/feed bytes, Sparkle update from the oldest supported installation, and existing permission/identity continuity. Public appcast retrieval was blocked in this session; local receipts report completed publication, which is weaker than a fresh public feed check. Preserve Developer ID identity, bundle ID, Sparkle signing key and current appcast URL. Keep dependency lockfiles enforced; RoyalVNC/CryptoSwift use moving branch requirements. Verify bundled license notices: the inspected simulator bundle contained no obvious license/acknowledgment resources, while RoyalVNC's checked-out MIT license requires notices in redistributed copies.

## What already looks sound

The project uses ScreenCaptureKit, VideoToolbox, binary encrypted media and native AVFoundation rendering. Capture is demand-driven; frame capture and cursor telemetry are bounded/coalesced in several stages. Pairing uses transcript-bound X25519 proofs, encrypted acceptance, host identity pinning, device-specific resume credentials, revocation persistence and bounded unauthenticated connections. Optional feature capabilities already support mixed versions. The Mac release tooling preserves the update identity, handles notarization/Sparkle signing, defers an update while sessions are active, and has recovery tests.

The practical order is: fix privacy packaging/disclosures and host identity fallback; fix idle keyframes, bounded media delivery and congestion adaptation together; correct the smaller trust/input/storage/setup defects; then qualify the exact iOS/Mac pair with real-device, paid-access, cloud-sync and Store checks. Passing unit tests and notarization alone do not satisfy those gates.
